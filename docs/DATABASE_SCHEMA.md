# Database Schema

All tables use a UUID primary key (`id`), plus `created_at`/`updated_at`
timestamps (server-side defaults). Generated by Alembic autogenerate from
the SQLAlchemy models — see `backend/alembic/versions/*_initial_schema.py`
for the literal DDL.

| Table | Key columns | Notes |
|---|---|---|
| `companies` | `student_id`, `name`, `company_type`, `industry`, `department`, `mission`, `description` | One row per generated internship company. Indexed on `student_id`, `company_type`. |
| `managers` | `company_id` (FK→companies), `name`, `title`, `personality`, `satisfaction_score` | 1:1 with company. |
| `projects` | `company_id` (FK), `title`, `role`, `technology_stack[]`, `difficulty`, `status`, `objectives[]`, `modules[]`, `deliverables[]`, `duration_weeks`, `start_date`, `end_date` | |
| `sprints` | `project_id` (FK), `sprint_number`, `name`, `goal`, `status`, `start_date`, `end_date` | Unique on `(project_id, sprint_number)`. |
| `tasks` | `sprint_id` (FK), `title`, `description`, `acceptance_criteria[]`, `priority`, `status`, `estimated_hours`, `deadline`, `started_at`, `completed_at`, `blocked_reason`, `deliverable_url` | Indexed on `status`, `priority`, `deadline`. |
| `task_dependencies` | `task_id` (FK→tasks), `depends_on_task_id` (FK→tasks) | `task_id` cannot move to `in_progress` until `depends_on_task_id` is `completed` (enforced in the API layer). Unique on the pair. |
| `team_members` | `company_id` (FK), `name`, `role`, `personality`, `skill_level` | **Live** — 3 generated per company at creation time; drives AI teammate chat (Feature 7). |
| `messages` | `company_id` (FK), `sender_type`, `sender_id`, `content` | **Live** — manager + teammate chat, real-time via WebSocket. |
| `notifications` | `company_id` (FK), `notification_type`, `message`, `is_read` | **Live** — created by chat, bug reports, and workflow-engine rule firings. |
| `events` | `project_id` (FK), `event_type`, `description`, `payload` (JSONB) | **Live** — created via the single `trigger_event(...)` entry point (automatic from workflow rules, or manual via `POST .../events/trigger`). |
| `activity_logs` | `company_id` (FK), `actor`, `action`, `detail`, `metadata_json` (JSONB) | **Live** — logs chat sends, events, and meeting completions. |
| `project_states` | `project_id` (FK, unique), `completed_tasks`, `pending_tasks`, `avg_completion_time_hours`, `missed_deadlines`, `bug_count`, `communication_frequency`, `stress_level`, `manager_satisfaction`, `team_satisfaction`, `current_sprint_number` | **Live** — synced on every task status transition and read/written by the Feature 8 workflow engine. |
| `meeting_schedules` | `project_id` (FK), `meeting_type`, `scheduled_at`, `agenda`, `participants[]`, `notes`, `attendance[]`, `action_items[]`, `completed` | **Live** — 8 auto-generated per project (Sprint Planning + Review × 4 sprints); completable via API. |
| `sprint_reviews` | `sprint_id` (FK, unique), `summary`, `velocity_completed_points`, `manager_feedback` | Schema ready — not yet populated by a generator; a natural Sprint Review chat/summary follow-up. |

## Enums (`app/models/enums.py`)

`CompanyType`, `DifficultyLevel`, `ProjectStatus`, `SprintStatus`,
`TaskStatus`, `TaskPriority`, `ManagerPersonality`, `MessageSenderType`,
`NotificationType`, `EventType`, `MeetingType` — all defined once and
reused across models/schemas so the API and DB never disagree on valid
values.

## Migrations

```bash
cd backend
alembic revision --autogenerate -m "description of change"
alembic upgrade head
```

The initial migration (`initial schema`) was generated and applied against
a real PostgreSQL 16 instance while building this repo — all 14 tables
confirmed present via `information_schema.tables` (see
`docs/VERIFICATION.md`).
